# Plan 04-02: Contextual Claim Verification Specification (Adjusted Scope)

## 1. Objective and Phase Context

Phase 4 transitions TRUTHNET AI into an investigative intelligence workbench. While Plan 04-01 established **what** is being asserted (`ClaimRecord`), Plan 04-02 establishes **how** available evidence relates to that assertion.

### Separation of Concerns
1. **Extraction (04-01 - Closed)**: Decomposes unstructured text, captions, OCR, and transcripts into atomic factual propositions (`ClaimRecord`), preserving source offsets, language provenance, surface syntax polarity, and attribution flags.
2. **Retrieval & Source Independence (04-03 - Future Wave)**: Gathers candidate external evidence items (`EvidenceItem`s) from local ClaimReview archives, Google Fact Check Tools API, and media registries, and performs multi-signal publisher/reporting dependency analysis.
3. **Contextual Verification (04-02 - Current Plan)**: Evaluates the relationship between an extracted claim and an arbitrary set of evidence items (whether from historical media matches, local investigation artifacts, or explicit caller-supplied items), computing passage-level alignment, temporal/spatial observational signals, and conservative classifications using deterministic verification.
4. **Human Review (04-02 / Workbench UI)**: Enables professional investigators to inspect evidence chains, confirm, dispute, or override system assessments with persistent rationale and notes.

## 2. Strict Scope Boundaries

### IN SCOPE for Plan 04-02
- Data models for assessment records (`ClaimAssessmentRecord`) and relational evidence citations (`ClaimEvidenceRelationRecord`).

## 5. Verification Model & Deterministic Reasoning Architecture

TRUTHNET enforces core epistemological principles:
1. **Never confuse model predictions with verified facts.**
2. **Missing evidence is NOT proof of falsehood.** When no relevant evidence is available, the claim must be classified as `UNVERIFIED` or `INSUFFICIENT_EVIDENCE`.
3. **Deterministic Verification Pipeline**:
   - **Step 1: Contextual Signals Analysis**:
     - Evaluates caption framing for archival keywords ("File Photo", "Archive", "Retrospective", "Flashback", "Remembering"). Archival keywords flag legitimate retrospective context to prevent false accusations of media manipulation, but **never independently establish that the underlying claim is SUPPORTED**.
   - **Step 2: Temporal Invariant Evaluation**:
     - Distinguishes 7 timestamps. Checks physical sequence invariants (e.g. publication predating capture).
     - Identifies temporal divergence between claimed date and observed historical timestamps.
   - **Step 3: Geographical Observational Evaluation**:
     - Computes Haversine distance between reference points and camera GPS.
     - Treats distances as observational signals without fixed universal thresholds.
     - Preserves camera location vs event location distinctions. Requires corroborating context before identifying a geographical contradiction.
   - **Step 4: Evidence Alignment & Stance Detection**:
     - Aligns ClaimRecord propositions and entities against `EvidenceItem` passages.
     - Identifies verbatim passage excerpts ($\le 500$ chars) and exact character spans.
     - Detects syntactic negation conflicts (e.g. claim asserts action, evidence asserts negation).
     - Explicitly tags source independence as `UNKNOWN` rather than pretending multiple URLs equal independent corroboration.
   - **Step 5: Conservative Classification Synthesis**:
     - Synthesizes findings into exactly one of the six conservative classifications.
     - Generates primary rationale, contradiction details, epistemic limitations, and recommended investigator actions.

## 6. The Six Conservative Assessment Classifications

TRUTHNET rejects pseudo-scientific truth probabilities and absolute truth claims. It outputs one of six well-defined classifications:

| Classification | Meaning & Trigger Conditions | Disqualifiers | UI Presentation Contract |
|---|---|---|---|
| `SUPPORTED` | All core proposition elements (subject, predicate, object, event, date, location) align with credible evidence with zero unresolved contradictions. | Any unresolved contradiction, temporal clash, or relying solely on archival keywords without event corroboration. | Green badge; displays supporting excerpts; explicitly notes that source independence is UNKNOWN unless verified. |
| `CONTRADICTED` | Direct, substantive refutation of the core proposition by authoritative evidence, official records, or verified primary data with corroborating context. | Ambiguous wording, minor ancillary detail differences, or uncorroborated camera GPS distance alone. | Red badge; displays contradicting excerpts with exact refutation points. |
| `MISLEADING_OR_CONTEXT_MISSING` | Underlying media or factual core is authentic, but critical context (date, location, attribution, omitted details, or deceptive framing) is distorted. | Materially false core event that never happened (which is `CONTRADICTED`). | Amber badge; side-by-side comparison of claimed vs observed context. |
| `UNVERIFIED` | Claim is fresh, breaking, or unassessed; no corroborating or refuting evidence exists in available records. | Evidence is available but low quality (which is `INSUFFICIENT_EVIDENCE`). | Gray badge; explicit note: "Not proven false. Awaiting corroborating evidence." |
| `INSUFFICIENT_EVIDENCE` | Available evidence is sparse, low-relevance, or only tangentially addresses the claim. | Direct refutation or confirmation exists. | Muted purple badge; lists data gaps and compiled investigator questions. |
| `CONFLICTING_EVIDENCE` | Multiple credible sources report mutually incompatible accounts. | One source is fringe and the other is verified consensus. | Orange badge; highlights divergent claims side-by-side; preserves disagreement. |

## 7. Evidence Alignment & Stance Detection

Every evidence item linked to an assessment receives a specific relationship type:
- `SUPPORTS`: Direct corroboration of the claim or proposition.
- `CONTRADICTS`: Direct refutation of the claim or proposition.
- `PROVIDES_CONTEXT`: Provides essential background, baseline figures, or chronological context without directly confirming or refuting.
- `PARTIALLY_SUPPORTS`: Corroborates some elements (e.g. location, participants) but not the key consequence.
- `PARTIALLY_CONTRADICTS`: Refutes specific ancillary assertions while leaving others intact.
- `DOES_NOT_ADDRESS`: Evidence discusses related topics but contains no information relevant to the claim proposition.
- `TEMPORAL_CONFLICT`: Evidence establishes that the timing of the claimed event is chronologically incompatible.
- `GEOGRAPHICAL_CONFLICT`: Evidence establishes that the physical location of the event or media capture is geographically incompatible (with corroborating context).

### Grounding Requirements
- `excerpt`: Verbatim text string ($\le 500$ characters) extracted directly from `EvidenceItem.content_or_passage`.
- `passage_span_start` and `passage_span_end`: Exact character offsets in source text.
- Full provenance retained: `source_publisher`, `source_published_date`, `source_retrieved_date`.
- `source_independence_status`: Set to `"UNKNOWN"` by default.

## 8. Temporal & Geographical Context Engine

### 8.1 Temporal Context (7 Distinct Timestamps)
1. `event_time`: When the real-world event allegedly occurred.
2. `capture_time`: When media was recorded (e.g. EXIF `DateTimeOriginal`).
3. `publication_time`: When content was published online.
4. `archive_time`: When an archival snapshot was recorded (Wayback, FactCheck archive).
5. `retrieval_time`: When TRUTHNET retrieved the evidence.
6. `truthnet_observation_time`: When TRUTHNET first ingested the submission.
7. `submission_time`: When the investigator submitted the evidence.

#### Physical Sequence Invariants & Rules
- Invariant 1: $t_{\text{capture}} \le t_{\text{publication}} \le t_{\text{archive}} \le t_{\text{retrieval}}$.
- Invariant 2: For live event media, $t_{\text{capture}} \approx t_{\text{event}}$. If $t_{\text{claimed\_event}} - t_{\text{observed\_capture}} > 30\text{ days}$ without archival caption signals, flag potential recycling signal.
- Invariant 3: $t_{\text{claimed\_event}} < t_{\text{observed\_capture}}$ represents physical sequence impossibility (alleging an event happened before the photo was taken). Flag as `TEMPORAL_CONFLICT`.
- **Archival Caption Rule**: Captions with "File Photo", "Archive", "Retrospective", or "Flashback" are flagged as `archival_signal_detected = True`. This signals legitimate archival reuse context to prevent false manipulation flags, but **never independently makes the claim `SUPPORTED`**.

### 8.2 Geographical Context (6 Distinct Location Types)
1. `claimed_location`: Location asserted in caption or claim text.
2. `source_reported_location`: Location reported by external news/fact-checker.
3. `media_metadata_location`: Location from container/file metadata.
4. `camera_device_gps_location`: GPS coordinates from EXIF hardware metadata.
5. `user_submitted_location`: Location entered by investigator.
6. `inferred_location`: Location inferred from landmarks, signage, or language.

#### Cautious Geodesic Calculation & Spatial Safeguards
- Calculate Great-Circle distance using Haversine formula on WGS-84 sphere ($R = 6,371.0\text{ km}$):
  $$\Delta\sigma = 2\arcsin\sqrt{\sin^2\left(\frac{\Delta\phi}{2}\right) + \cos\phi_1\cos\phi_2\sin^2\left(\frac{\Delta\lambda}{2}\right)}$$
  $$d = R \cdot \Delta\sigma$$
- **No Universal Distance Threshold**: Do not use a fixed 30 km radius as a universal truth criterion. Distance is recorded as an observational quantitative metric.
- **Observational Signals**: Centroid distance and camera GPS are observational signals, not proof of fraud.
- **Corroborating Context Requirement**: A geographical contradiction (`GEOGRAPHICAL_CONFLICT` or `CONTRADICTED`) requires corroborating context (e.g. news reports or multiple sources placing the event in a completely different city/country), not just a solitary distant camera GPS reading.
- **Camera vs Event Caveat**: Every spatial comparison must include the explicit epistemic disclaimer: "Camera GPS indicates device position at capture time, which may differ from event location in telephoto, aerial, or drone photography. City reference points are geographic centroids, not forensic coordinates."

## 9. Assessment Persistence, Versioning, and Human Review Lifecycle

### 9.1 Immutability & Versioning
- Assessment records are immutable. When new evidence arrives or re-verification is requested:
  1. A new `ClaimAssessmentRecord` is created with `version = current_max_version + 1`.
  2. Prior active assessment is marked `is_active = False` with `supersede_reason = "REVERIFICATION_WITH_NEW_EVIDENCE"`.
  3. All historical versions remain queryable via `/assessment/history`.

### 9.2 Human Review State Machine
- `UNREVIEWED`: Initial system-generated state.
- `CONFIRMED`: Investigator agrees with classification and evidence alignment.
- `DISPUTED`: Investigator disputes findings (notes recorded, classification flagged).
- `MODIFIED`: Investigator overrides classification or adds manual evidence citations.
- Audit fields: `reviewed_by`, `human_reviewer_notes`, `human_reviewed_at`.

## 10. Pipeline Integration with Safe Failure Handling

- In `backend/app/services/pipeline.py`:
  - After `_extract_and_persist_claims()` completes successfully, the pipeline inspects whether relevant local evidence exists for the submission:
    * Historical `MediaMatchRecord`s linked to the submission's media asset.
    * Ingested technical metadata from `ExtractionRecord`.
  - If relevant local evidence exists: automatically triggers initial contextual verification for each extracted claim.
  - If no usable evidence exists: claims remain unassessed or in an explicit `UNVERIFIED` state. **The absence of evidence is never interpreted as proof of falsehood.**
  - **Fault Isolation**: Verification is wrapped in an explicit `try...except` block. A failure in verification logs a warning and does NOT fail the pipeline, does NOT roll back claim extraction, and does NOT interrupt evidence intake.

## 11. API Endpoints & Request/Response Schemas

### Endpoints (in `backend/app/api/v1/claims.py`)
1. `POST /api/v1/claims/{claim_id}/verify`: Executes contextual verification against provided or locally discovered evidence items.
2. `GET /api/v1/claims/{claim_id}/assessment`: Retrieves the current active assessment with all evidence relations.
3. `GET /api/v1/claims/{claim_id}/assessment/history`: Retrieves full audit history of all versions.
4. `POST /api/v1/claims/{claim_id}/assessment/{assessment_id}/review`: Submits human investigator review (`CONFIRMED`, `DISPUTED`, `MODIFIED`).
5. `GET /api/v1/submissions/{submission_id}/assessments`: Retrieves active assessments for all claims extracted from a submission.
